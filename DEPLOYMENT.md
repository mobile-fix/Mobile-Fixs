# Deploying MyMobiFix to Render + a GoDaddy domain

Everything in the codebase is ready. What remains needs your accounts, so the
steps below are split into **you do this** and **already done**.

---

## Already done

- PostgreSQL datasource, with a regenerated initial migration (15 tables, 39
  indexes, 16 foreign keys) at `prisma/migrations/0_init/`.
- Every text search given `mode: "insensitive"`. Prisma's `contains` is
  case-insensitive on SQLite but **case-sensitive on Postgres** — without this,
  searching "iphone" would silently stop matching "iPhone" in production.
- Demo bookings, reviews and enquiries gated behind `SEED_DEMO_DATA`. Production
  seeds the device catalogue and the owner account only, so no invented
  testimonials or phantom repair counts go live.
- `NEXT_PUBLIC_USES_DEMO_DATA` controls the "demonstration deployment" banners.
- `render.yaml` blueprint defining the web service and the database.
- Git repository initialised and committed. `.env` and `prisma/dev.db` are
  ignored; the commit was checked and contains no secrets.

## Step 1 — Push to GitHub (you)

Render deploys from a Git remote, so the code has to live on GitHub first.

Create an empty repository at <https://github.com/new> — **private** is fine and
recommended. Do not let GitHub add a README, `.gitignore` or licence; the repo
already has them.

Then, from `D:\MOBILE-FIX`:

```bash
git remote add origin https://github.com/YOUR-USERNAME/mymobifix.git
```

```bash
git push -u origin main
```

## Step 2 — Create the Render services

**Prerequisite:** a payment method on the workspace (see the box below) and the
GitHub account connected to Render, so it can read the private repository.

In the Render dashboard: **New → Blueprint**, select the repository. Render reads
`render.yaml` and creates both the web service and the PostgreSQL database.

It will prompt for the values marked `sync: false`, which are deliberately not
in the repo:

| Variable | What to enter |
|---|---|
| `SEED_ADMIN_EMAIL` | The email you want to sign in to `/admin` with |
| `SEED_ADMIN_PASSWORD` | A strong password — this becomes your owner account |
| `NEXT_PUBLIC_SUPPORT_PHONE` | Your real business phone |
| `NEXT_PUBLIC_SUPPORT_EMAIL` | Your real support email |
| `NEXT_PUBLIC_WHATSAPP_NUMBER` | Digits only with country code, e.g. `919876543210` |
| `NEXT_PUBLIC_BUSINESS_HOURS` | e.g. `Mon–Sat, 9:00 AM – 8:00 PM IST` |
| `NEXT_PUBLIC_BUSINESS_ADDRESS` | Your real service-centre address |

`SESSION_SECRET` is generated by Render automatically. `DATABASE_URL` is wired
from the database. Neither needs your input.

### A payment method is required before anything can be created

Render's API refuses resource creation on a workspace with no card on file:

    402: Payment information is required to complete this request.

This applies to **free-tier resources too**, and it is not mentioned in
<https://render.com/docs/free>. Add a card at
<https://dashboard.render.com/billing> before creating the services.

Adding a card does not itself charge anything — free plans stay at $0. It is an
anti-abuse verification step. Set a **spend limit** on the billing page at the
same time if you want a hard guarantee against surprise charges.

### Free-tier limits

Once a card is on file, deploying on these plans costs nothing. Render's stated
free-tier terms
(<https://render.com/docs/free>) — check the pricing page for current figures:

- **Free web service:** 0.1 CPU / 512 MB RAM. Spins down after **15 minutes**
  without inbound traffic and takes about **a minute** to restart, so the first
  visitor after a quiet spell waits. You get **750 free instance-hours per month
  per workspace**; spun-down time does not consume them.
- **Free PostgreSQL:** 1 GB storage, and it **expires 30 days after creation**.
  The database then becomes inaccessible, with a **14-day grace period** to
  upgrade before Render deletes it and all its data.
- **Bandwidth** counts against a monthly allowance; exceeding it suspends the
  service unless a payment method is on file.

Practical reading: free is fine for putting the site online and showing people.
Before you advertise it or take a real booking, move the web service to Starter
(so it never sleeps) and the database to a paid plan (so it is not deleted at day
30, and gets backups).

## Recommended: use Neon for the database instead of Render's

Render's free PostgreSQL **expires 30 days after creation** and is then deleted —
the single biggest risk in this whole setup, because it takes real customer
bookings with it.

[Neon](https://neon.com) has a free Postgres tier that does **not** expire.
Its docs state plainly that when you hit the free limits, *"None of these limits
delete your data."*

Sized against this project:

| | Neon free | This app |
|---|---|---|
| Storage | 0.5 GB | 9.2 MB catalogue + ~3.75 kB per booking |
| Capacity | — | **~130,000 bookings** |
| Compute | 100 CU-hours/month | 0.25 CU for ~400 h/month |
| Expiry | none | — |

To use it, create a Neon project, copy its connection string, and set
`DATABASE_URL` on the Render web service to that value instead of wiring it
`fromDatabase`. Then delete the `databases:` block from `render.yaml` so Render
does not create one it will later delete.

Everything else — migrations, seeding, the app — is unchanged: it is the same
PostgreSQL either way.

## Step 3 — Seed the catalogue (once, after the first deploy)

The build runs `prisma migrate deploy`, which creates the tables but inserts no
data. Free Render instances have no Shell tab, so run the seed once from your own
machine with `DATABASE_URL` set to the database's **External** connection string:

```bash
npm run db:seed
```

That creates 11 brands, 57 device models, 12 services, ~1,265 prices, and the
owner account from `SEED_ADMIN_EMAIL` / `SEED_ADMIN_PASSWORD`. It is idempotent,
so running it twice is harmless.

> Only the owner account is created. The demo manager and technician accounts —
> whose passwords are published in the README — are created only when
> `SEED_DEMO_DATA=true`, so they never exist on a real deployment.

## Step 4 — Connect your GoDaddy domain

### 4a. Add the domain in Render

Web service → **Settings → Custom Domains → Add Custom Domain**.

Add both:
- `mymobifix.com`
- `www.mymobifix.com`

Render then shows you the exact DNS target — it looks like
`mymobifix.onrender.com`. Use the value Render gives you, not the example here.

### 4b. Set the records in GoDaddy

GoDaddy → **My Products → your domain → DNS → Manage Zones**.

| Type | Name | Value | TTL |
|---|---|---|---|
| `CNAME` | `www` | the `*.onrender.com` host Render showed you | 600 |
| `A` | `@` | the IPv4 address Render shows for the apex | 600 |

Notes that trip people up:

- **GoDaddy cannot CNAME the apex** (`mymobifix.com` with no `www`). Render
  provides an A record for the apex — use that. Alternatively, set the apex to
  forward to `www` under GoDaddy's *Forwarding* section and run the site on
  `www`.
- Delete GoDaddy's default `A @ → Parked` record, or it will fight yours.
- Remove any pre-existing conflicting `CNAME www` record first.
- DNS usually propagates in 10–30 minutes; GoDaddy can take up to an hour.

### 4c. Point the app at the real domain

Once Render shows the domain as **Verified**, update this env var on the web
service and redeploy:

```
NEXT_PUBLIC_SITE_URL = https://www.mymobifix.com
```

It backs canonical URLs, `sitemap.xml` and Open Graph tags, so search engines
and link previews point at the right domain. Forms keep working even while it
lags behind: the CSRF check also accepts the request's own `Host`.

TLS certificates are issued automatically by Render once DNS verifies.

## Step 5 — Go-live checklist

- [ ] `SESSION_SECRET` generated by Render (not the development value)
- [ ] Owner password is strong; seeded manager/technician accounts changed or deactivated
- [ ] Web service on a paid plan — no 15-minute sleep / 1-minute cold start
- [ ] Database on a paid plan **before day 30**, and backups enabled
- [ ] `NEXT_PUBLIC_SITE_URL` is `https://www.mymobifix.com`
- [ ] `NEXT_PUBLIC_USES_DEMO_DATA` left **unset** — demo banners off
- [ ] Real contact details set via `NEXT_PUBLIC_SUPPORT_*`
- [ ] `/terms`, `/privacy`, `/warranty` reviewed by a lawyer — they ship as
      clearly-labelled templates
- [ ] Prices reviewed in Admin → Catalogue. The seeded figures are illustrative,
      not your actual pricing
- [ ] Email/SMS/WhatsApp providers configured, or knowingly left off (the app
      reports them as "not configured" rather than pretending to send)

## Step 6 — Search and ads setup

Every value below is a Render environment variable (web service →
**Environment**). They are `NEXT_PUBLIC_*`, so they are baked in at build time:
after adding or changing any of them, use **Manual Deploy → Deploy latest
commit**. Each one is optional — the site leaves out whatever is unset.

### 6a. Business location (local SEO)

Google ranks repair shops for "near me" searches largely on location signals.
Set the ones that are true; leave the rest blank rather than guessing.

| Variable | Example |
| --- | --- |
| `NEXT_PUBLIC_BUSINESS_ADDRESS` | Shop 12, Galleria Market, DLF Phase 4 |
| `NEXT_PUBLIC_BUSINESS_CITY` | Gurugram |
| `NEXT_PUBLIC_BUSINESS_REGION` | Haryana |
| `NEXT_PUBLIC_BUSINESS_POSTAL_CODE` | 122009 |
| `NEXT_PUBLIC_BUSINESS_LATITUDE` / `_LONGITUDE` | Right-click the pin in Google Maps |
| `NEXT_PUBLIC_SERVICE_AREAS` | Gurugram, South Delhi, Noida |
| `NEXT_PUBLIC_BUSINESS_PROFILES` | Google Business Profile, Instagram and Facebook URLs, comma-separated |

Doorstep-only, no walk-in shop? Leave the street address blank and set the
city and service areas. The address placeholder is never published.

Then create a **Google Business Profile** (business.google.com) with exactly the
same name, phone number and address/service areas. It is the biggest single
lever for the map results. Ask every happy customer for a Google review.

### 6b. Google Search Console

1. search.google.com/search-console → **Add property** → **Domain** →
   `mymobifix.com`.
2. Google shows a `google-site-verification=…` TXT record. In GoDaddy →
   **My Products → mymobifix.com → DNS → Add New Record**: Type `TXT`, Name `@`,
   Value = that string. Save, wait ~10 minutes, click **Verify**.
3. **Sitemaps** → submit `https://www.mymobifix.com/sitemap.xml`.
4. **URL Inspection** → request indexing for `/`, `/services` and `/repair`.

(The `NEXT_PUBLIC_GOOGLE_SITE_VERIFICATION` variable is an alternative to the
DNS record, for the "HTML tag" method. One or the other is enough.)

### 6c. Google Analytics 4 + Google Ads

1. analytics.google.com → create a GA4 property and a **Web** data stream for
   `https://www.mymobifix.com` → copy the Measurement ID (`G-…`) into
   `NEXT_PUBLIC_GA4_ID`.
2. Google Ads → **Goals → Conversions → New conversion action → Website →
   set up manually**. Create one action per row below, category as shown,
   "Count: One". For each, open **Tag setup → Install the tag yourself** and
   copy from the event snippet: the `AW-…` ID (same for all) into
   `NEXT_PUBLIC_GOOGLE_ADS_ID`, and the label after the slash into the
   variable for that action.

   | Conversion action | Category | Variable |
   | --- | --- | --- |
   | Booking submitted (make this **Primary**) | Book appointment | `NEXT_PUBLIC_GOOGLE_ADS_BOOKING_LABEL` |
   | WhatsApp chat click | Contact | `NEXT_PUBLIC_GOOGLE_ADS_WHATSAPP_LABEL` |
   | Call click | Phone call lead | `NEXT_PUBLIC_GOOGLE_ADS_CALL_LABEL` |
   | Contact form | Submit lead form | `NEXT_PUBLIC_GOOGLE_ADS_CONTACT_LABEL` |

3. Link GA4 and Google Ads (GA4 Admin → **Product links → Google Ads**).

### 6d. Meta Pixel

1. Meta Events Manager → **Connect data sources → Web → Meta Pixel** → copy
   the Pixel ID into `NEXT_PUBLIC_META_PIXEL_ID`.
2. Business Settings → **Brand safety → Domains → Add** `mymobifix.com` → choose
   **DNS TXT** and add that record in GoDaddy the same way as 6b (or choose
   the meta-tag method and put its `content` value in
   `NEXT_PUBLIC_META_DOMAIN_VERIFICATION`).
3. Events Manager → **Aggregated Event Measurement**: rank `Schedule` (bookings)
   first, then `Contact` (WhatsApp/calls), then `Lead` (contact form).

### What the site reports

| What happened | GA4 | Google Ads | Meta |
| --- | --- | --- | --- |
| Booking submitted | `generate_lead` (method `booking`) | booking label | `Schedule` |
| WhatsApp link clicked, anywhere | `generate_lead` (method `whatsapp`) | WhatsApp label | `Contact` |
| Phone number tapped | `generate_lead` (method `phone`) | call label | `Contact` |
| Contact form sent | `generate_lead` (method `contact_form`) | contact label | `Lead` |

No names, phone numbers, emails or form contents are sent to Google or Meta.
Check it is working with Google Tag Assistant (tagassistant.google.com) and
Meta's **Test events** tab.

### Before spending on ads

- Upgrade the Render web service off the free plan. A sleeping instance takes
  30–60 seconds to answer the first click, and that click is paid for.
- Send each ad group to the most specific page: an iPhone ad to
  `/repair/apple`, a battery ad to `/services/battery-replacement`.

## Known limitation on multi-instance scaling

Rate limiting is an in-process `Map` (`src/lib/rate-limit.ts`). It is correct for
a single instance, which is what Render runs by default. If you ever scale to
more than one instance, each gets its own counter and the effective limit
multiplies. Set `RATE_LIMIT_REDIS_URL` and swap the `hit()` implementation for a
Redis `INCR`+`EXPIRE`; the call sites and thrown error do not change.

## Local development after the Postgres switch

`DATABASE_URL` in your local `.env` still points at the old SQLite file, which is
no longer valid. Either point it at the Render database's **External** connection
string, or run Postgres locally:

```bash
# Port 5432 was already in use on this machine, so the running container uses 55432.
docker run --name mymobifix-db -e POSTGRES_PASSWORD=verifypass -e POSTGRES_DB=mymobifix -p 55432:5432 -d postgres:16
```

Then set in `.env`:

```
DATABASE_URL="postgresql://postgres:verifypass@localhost:55432/mymobifix?schema=public"
```

```bash
npx prisma migrate deploy && npm run db:seed
```
